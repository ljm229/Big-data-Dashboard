# 即时零售企业数据看板设计方案

**核心定位：以利润为核心的经营决策看板，而不是全量业务数据的展示墙。**

针对你们“管理层使用80%、运营使用20%”的场景，建议采用：

> **一套数据底座、统一指标口径、三级展示结构、五大经营模块，加一个贯穿全局的预警中心。**  
> 管理层看结果、差距、趋势和风险；运营沿着同一指标下钻，找到具体门店、渠道、商品和订单，完成整改。

首页优先回答四个问题：**赚了多少钱？距离目标差多少？问题集中在哪里？现在需要做什么决策？**

以下为建议的内部经营管理方案，不代表美团、饿了么或淘宝的官方指标口径。库存快照、流量、活动计划及接口日志等字段，需要核实你们实际可获取的范围；预警阈值均为初版示例，不能未经历史回测直接用于全部门店。

---

## 一、总体架构：一套数据，三级展示

### 1. 展示分层

| 层级 | 面向角色 | 展示内容 | 角色真实需求 | 设计原因 |
|---|---|---|---|---|
| **一级：经营决策首页** | 总经理、业务负责人、财务负责人 | 公司经营利润、目标差距、月底预测、盈利质量、主要风险、重点决策事项 | 快速判断业务是否健康，决定资源投向和干预重点 | 满足管理层高频需求，不要求管理层自行翻报表找问题 |
| **二级：经营专题汇总** | 管理层、城市负责人、运营负责人 | 城市、门店群、成本、渠道、品类的汇总分析与差异贡献 | 判断“哪里拖累利润、哪里值得增长、哪类问题优先处理” | 承接管理决策，不直接跳到海量明细 |
| **三级：诊断与整改明细** | 城市运营、门店运营、商品运营、履约运营、财务核算 | 门店诊断、小时异常、订单、商品、费用、履约节点、排查清单及整改记录 | 找到具体原因、责任对象和处理动作，并验证是否恢复 | 明细服务执行，通过下钻进入，不占用首页空间 |

**80%与20%的体现是默认视角和信息优先级不同，不是把两类用户做成两套互不相通的报表。**

### 2. 模块导航

建议导航保留六个入口：

**经营总览｜城市门店经营｜利润成本拆解｜渠道订单大盘｜商品品类大盘｜经营预警中心**

订单明细、商品明细、费用流水、履约轨迹、异常工单等，全部作为下钻页面，**不设置为首页内容，也不作为一级导航的主入口。**

---

## 二、数据底座与指标口径：先保证“算得对”，再保证“看得懂”

### 1. “一套数据源”不是“一张大宽表”

建议以翱象业务数据为主，统一形成订单、商品、费用、履约、库存等事实数据，共用城市、门店、渠道、商品和时间维度，再由统一指标层供给所有页面。事实表与维度表分离、事实保持一致粒度，是适合此类分析模型的设计基础。

| 数据域 | 建议最小粒度 | 主要用途与控制点 |
|---|---|---|
| 订单主表 | 一笔业务订单 | 支付、取消、完成、来源渠道；统一订单唯一标识，防止跨系统重复计数 |
| 订单商品表 | 订单×商品行 | 数量、成交收入、商品成本、优惠分摊；不能把订单金额重复到每条商品行后直接求和 |
| 退款、结算与费用 | 一笔退款或费用流水 | 退款、佣金、配送费、投放、补贴、赔付；明确是否已在收入中扣除 |
| 履约事件 | 订单×履约节点事件 | 接单、拣货、出库、骑手接单、送达、承诺时间；保留各节点时间 |
| 库存与上下架快照 | 门店×商品×快照时间 | 可售库存、缺货、上下架、库存覆盖时长；库存不能跨时间直接累加 |
| 目标、成本与经营配置 | 门店/城市×日期或期间 | 利润预算、固定成本、计划营业时间、活动计划、责任人及配置变更 |

**需要补齐的不是另一套报表，而是共用的管理数据：**利润目标、成本归集规则、活动日历、计划营业时间、责任人映射，以及告警所需的数据健康状态。

### 2. 利润分层：不要把毛利当成最终盈利

建议建立以下管理口径，并由财务、业务共同确认：

| 指标 | 建议定义 | 主要服务的决策 |
|---|---|---|
| **经营净收入** | 归属于商家的商品、包装、配送等经营收入，加可确认且未重复计入的补贴，减退款；商家优惠按净额处理 | 业务真正取得多少经营收入 |
| **商品毛利** | 商品净收入－对应商品销售成本 | 商品定价、采购成本、品类结构是否合理 |
| **订单贡献利润** | 经营净收入－商品成本－渠道费用－履约变动成本－耗材－营销费用－相关赔付及损失，均避免重复扣减 | 增加这类订单，是否有助于覆盖固定成本 |
| **门店经营利润** | 门店订单贡献利润合计－门店固定及期间成本－未归入订单的门店费用 | 门店是否具备持续经营价值 |
| **公司经营利润** | 门店经营利润合计－尚未计入的城市及总部经营费用＋未归店经营收益 | 公司整体经营是否赚钱 |
| **单均贡献利润** | 同一统计范围内的订单贡献利润÷对应完成订单数 | 增长质量有没有变差 |

这里的“公司经营利润”是管理口径，**不能在尚未完成税费、财务费用等科目处理时直接命名为“净利润”。**

必须统一以下处理规则：

| 关键问题 | 建议处理 |
|---|---|
| 优惠与平台扣费重复计算 | 商家优惠已从收入扣除的，不再作为成本重复扣；不能用已扣佣金、运费的到账金额作为收入后再次扣费 |
| 取消、退款订单 | 订单量按定义处理，但已经发生且无法退回的配送、耗材、赔付等成本不能被一并过滤掉 |
| 实时利润与结算利润 | 区分“预估”“已校准”“已关账”，显示截止时间、成本覆盖率和调整记录 |
| 跨期退款和补贴调整 | 保留订单经营归属与财务记账日期两套时间视角，通过调整表对账，不悄悄覆盖已关账结果 |
| 利润率、完成率等比率 | 汇总后用总分子÷总分母，不能直接平均各门店百分比 |
| 渠道、品类的全成本利润 | 默认展示贡献利润；涉及固定成本分摊时明确标识分摊规则，不能把分摊结果当成直接可控成本 |
| 目标为零或负数 | 不展示容易误导的达成率，改为展示实际与目标的金额差额及改善幅度 |

### 3. 全站指标优先级

**第一优先级：经营利润、利润目标差距、单均贡献利润、严重经营风险。**

**第二优先级：经营净收入、有效订单增长、同店增长、盈利门店覆盖。**

**第三优先级：渠道、商品、库存、履约和投放效率。**

GMV和订单量可以展示，但不占据首页最核心位置。**不能因为单量增长就标记“经营向好”，也不能因为单量下降就默认“利润受损”。**

## 三、模块一：经营总览——管理层的默认首页

**面向角色：**总经理、业务负责人、财务负责人。

**角色真实需求：**不用进入明细，也能判断整体盈利、目标完成可能性和当前最重要的经营动作。

### 展示内容与设计原因

| 展示区域 | 展示内容 | 设计原因 |
|---|---|---|
| **顶部核心指标卡** | 经营利润、利润进度差额、月底预测与目标缺口、经营利润率、单均贡献利润、亏损门店数及亏损额 | 把利润总量、增长质量和经营底部风险放在第一屏 |
| **目标与趋势区** | 累计利润实际线与进度目标线；近期利润、利润率趋势 | 区分短期波动与持续偏离，避免只看单日结果 |
| **差距来源区** | 对利润差距贡献最大的城市、成本项、渠道，各展示少量重点项 | 不只告诉管理层“没达标”，还要指出优先处理方向 |
| **辅助规模区** | 经营净收入、完成订单、同店增长、新店贡献 | 用规模解释利润，而不是用规模替代利润 |
| **风险摘要区** | 红/黄告警数、受影响门店数、主要风险类型、预计利润风险敞口、重点事件摘要 | 管理层看影响范围与严重程度，不看完整告警流水 |
| **经营结论区** | 最多三条“结论＋依据＋建议动作＋责任部门” | 把图表转化为可讨论、可执行的管理议题 |

### 目标差距必须采用“经营进度”，不能机械按月天数计算

建议：

**利润进度差额＝累计实际利润－截至当前的累计预算利润。**

预算需要考虑营业日、周末、活动安排和新店爬坡；月底预测采用“已实现利润＋剩余日期预测利润”，同时显示预测区间及主要假设。

首页默认查看本月累计，核心财务卡使用一致截止时间；**今日实时快报单独展示预估贡献利润与订单表现，不与已校准利润混成一个未经标注的数字。**

### 首页明确不放什么

不放订单列表、SKU列表、费用流水、全部门店排名和完整排查清单。最多保留少量异常事件摘要，点击后进入对应专题。

**典型下钻：**利润进度差额 → 城市差距贡献 → 门店诊断 → 成本或订单明细。

## 四、模块二：城市门店经营——决定资源向哪里投、问题从哪里改

**面向角色：**管理层、城市负责人；运营下钻使用。

**角色真实需求：**判断哪些城市值得加资源，哪些门店需要保利润、补能力或专项整改，而不只是知道谁的销售额最高。

### 展示内容与设计原因

| 展示内容 | 建议形式 | 设计原因 |
|---|---|---|
| 城市利润贡献、利润目标差额 | 利润贡献条形图、目标差距排序 | 按对公司利润的影响排序，而非按销售规模排序 |
| 城市增长与盈利质量 | 横轴为同店收入增长，纵轴为经营利润率，气泡大小为收入规模 | 同时识别“健康增长”和“增收不增利” |
| 盈利与亏损门店结构 | 盈利店占比、亏损店数量、亏损总额、连续亏损分布 | 防止少数头部门店掩盖大量门店经营问题 |
| 同店与新店拆分 | 同店经营变化、新店新增利润、爬坡期表现 | 防止把扩店带来的增长误认为原有门店改善 |
| 门店经营分型 | 可扩量、需保利、需整改、爬坡观察 | 将汇总分析直接对应管理动作 |
| 门店履约与承接能力摘要 | 高风险门店数、产能受限门店数、核心商品缺货影响 | 避免给无法承接订单的门店继续加投放 |

### 门店分型与动作

| 门店类型 | 识别重点 | 建议动作 |
|---|---|---|
| **盈利且增长** | 利润、单均贡献、履约能力同步健康 | 在库存和产能允许范围内增加资源 |
| **增长但利润变差** | 单均贡献下降、补贴或履约成本上升 | 优先调商品结构、优惠和费用，不盲目继续冲量 |
| **盈利但订单下降** | 贡献利润仍健康，需求或转化走弱 | 排查营业、供给、流量和活动变化，判断是否值得恢复规模 |
| **持续亏损** | 经营性亏损、爬坡投入、成本分摊分别识别 | 制定专项整改，必要时进行经营调整评估 |

**亏损不直接等于关店。**建议同时看门店成熟度、可避免成本、整改空间及退出影响，避免用单月分摊利润作出过度简化的决策。

**运营下钻：**城市 → 门店经营诊断 → 渠道/小时/品类 → 订单、商品或费用证据。

**整改产出：**责任人、主要问题、处理动作、预计改善指标、完成时限和复查结果。

## 五、模块三：利润成本拆解——解释“利润为什么变化”

**面向角色：**总经理、财务负责人、业务负责人；城市和运营负责人定位可控问题。

**角色真实需求：**分清利润变化来自订单规模、商品结构、成本上涨、营销投入还是履约损失，找到最值得优先处理的利润问题。

### 展示内容与设计原因

| 展示内容 | 建议形式 | 设计原因 |
|---|---|---|
| **收入到利润的完整路径** | 利润瀑布图：收入→商品成本→渠道费用→履约费用→营销费用→门店成本→公司经营利润 | 建立统一的利润认知，避免各部门只看自己的局部指标 |
| **本期与目标/上期利润差异** | 利润变化桥接图 | 把差额拆为规模、结构、价格成本、履约、营销、固定成本和调整项 |
| **重点费用双视角** | 费用金额、费用率、单均费用并列 | 区分“规模增长导致总费用增加”和“效率真正变差” |
| **利润漏损汇总** | 负贡献订单占比、异常优惠、赔付退款损失、异常配送成本、成本缺失金额 | 优先发现可整改的利润流失 |
| **补贴与结算风险** | 已确认/待确认补贴、结算差异、成本覆盖率 | 防止把尚未确认的收益当作稳定盈利 |
| **经营情景测算** | 调价、减补贴、增单、补人的利润影响区间 | 支持管理层比较方案，不把测算当成结果承诺 |

### 两个重要设计要求

**第一，利润变化拆解必须能对账。**规模、结构、单价和成本之间存在交叉影响，需固定拆解方法，保留调整项，确保所有贡献相加等于真实利润差额。

**第二，费用必须区分可直接归属和分摊。**订单可直接归属的费用进入订单贡献；门店固定成本保留在门店层；总部公共费用明确分摊规则。不能因为某品类分摊了较多租金，就直接认定该品类应该下架。

**运营下钻：**利润下降项 → 城市/门店 → 渠道/品类 → 订单费用或商品成本明细。

## 六、模块四：渠道订单大盘——看订单质量，不只看订单数量

**面向角色：**管理层、渠道负责人、活动运营和履约负责人。

**角色真实需求：**判断哪些渠道带来可持续利润，哪些订单虽然拉高规模，却消耗补贴、库存和履约能力。

渠道应按你们实际接入的成交渠道和来源入口定义，不默认已经营其他平台。**成交渠道与流量入口要分开：同一订单经过多个入口，不能在渠道总量中重复计数。**

### 展示内容与设计原因

| 展示内容 | 建议形式 | 设计原因 |
|---|---|---|
| 渠道贡献利润、单均贡献、利润率 | 渠道盈利对比 | 决定预算和资源分配，而不是只比较渠道销售额 |
| 渠道规模与利润结构 | 收入份额、订单份额、利润贡献金额及变化 | 识别高规模低利润渠道；总利润接近零时避免展示失真的利润占比 |
| 订单生命周期 | 支付→接单→拣货→配送→完成，各阶段转化与损失 | 定位订单损失发生在哪个环节 |
| 订单质量 | 负贡献订单占比、取消率、退款损失、超时率、赔付成本 | 把订单增长与利润、履约质量绑定 |
| 小时订单分布 | 实际曲线、正常区间、活动标记、异常标记 | 看清渠道时段结构，并与预警中心联动 |
| 活动投入与补贴依赖 | 商家投入、确认补贴、活动订单贡献、预算消耗 | 区分健康经营与依靠补贴维持的表面增长 |

### 口径注意

流量数据可获取时，再增加“曝光→进店→下单→支付”漏斗；未获取时标记“未接入”，不能根据订单下跌直接得出“平台限流”的结论。

完成率、退款率、履约表现应使用可比订单群组和观察期限，不能把尚在配送中的当小时订单全部视为未完成异常。

活动页面可以展示“归因订单的收入和利润”，但没有对照或可靠增量测算时，**不能将其直接称为活动新增利润。**

**运营下钻：**渠道 → 城市/门店 → 活动或小时 → 异常订单与履约节点。

## 七、模块五：商品品类大盘——让选品、库存与利润联动

**面向角色：**管理层、商品负责人、采购负责人；商品和门店运营下钻使用。

**角色真实需求：**知道哪些品类真正赚钱，哪些商品值得保供，哪些商品占用库存但贡献不足，以及缺货是否正在伤害订单和利润。

### 展示内容与设计原因

| 展示内容 | 建议形式 | 设计原因 |
|---|---|---|
| 品类利润结构 | 品类毛利、分摊贡献利润、收入与利润变化 | 不用销售额替代商品经营价值 |
| 品类增长与盈利质量 | 增长—利润率矩阵 | 区分应扩张、应调价和应优化的品类 |
| 商品经营结构摘要 | 高贡献畅销、低毛利引流、高毛利低动销、负贡献商品的数量与影响 | 管理层看结构，运营下钻处理具体SKU |
| 核心商品保供 | 核心商品缺货率、预计缺货影响、库存覆盖时长 | 将补货优先级与订单承接、利润贡献关联 |
| 库存效率 | 库存金额、周转、滞销、损耗；具备批次数据时增加临期风险 | 同时关注利润和资金占用 |
| 价格与成本变化 | 采购成本上涨影响、售价变化、优惠后的贡献变化 | 定位商品利润恶化的具体来源 |

**核心商品缺货率建议采用预期需求加权，而不是只数缺货SKU个数。**否则一个高频刚需商品断货，可能被大量低销量正常在售商品稀释。

商品履约费用分摊需透明展示规则；商品关联订单数不能简单跨品类相加。对于低毛利商品，还要看所在购物篮的订单贡献，**不宜仅凭单品毛利低就直接下架。**

**运营下钻：**品类 → 子品类 → SKU → 城市/门店 → 库存、价格、成本和关联订单。

## 八、经营预警中心：小时级爆单与暴跌监控

### 1. 面向角色、真实需求与展示分层

| 层级 | 面向角色 | 展示内容 | 真实需求与设计原因 |
|---|---|---|---|
| 首页风险摘要 | 管理层 | 红黄告警数、影响范围、重大风险、预计利润影响 | 知道是否需要跨部门协调，不被大量单店通知打扰 |
| 预警专题 | 城市负责人、运营负责人 | 城市/门店异常分布、异常趋势、待处理事件和责任归属 | 判断优先级，调配人员和资源 |
| 事件诊断页 | 执行运营、店长、履约及技术人员 | 小时曲线、正常区间、证据、自动排查清单、处理记录 | 明确“为什么报、先查什么、谁来处理、如何确认恢复” |

预警排序以**严重程度、影响范围和预计利润影响**为主。严重缺货、无法履约或交易故障可以直接置顶，不因短期利润金额较小而被降级。

### 2. 小时展示，短周期计算

建议采用以下监控设计：

| 项目 | 建议方案 |
|---|---|
| 展示粒度 | 小时曲线与小时热力图 |
| 计算频率 | 数据条件允许时，每5分钟计算一次；实际频率受源数据到达能力约束 |
| 主检测窗口 | 最近60分钟，避免必须等整点才能发现问题 |
| 辅助窗口 | 最近15分钟，用于判断异常是否仍在持续、识别突发中断 |
| 检测层级 | 公司、城市、门店、门店×渠道；库存与产能再汇总到共享资源的门店层 |
| 主订单指标 | 按支付发生时间统计的新增支付订单数；后续取消退款另行监控，不回头改写原始需求信号 |
| 时间对齐 | 当前14:00—14:20，只能与历史可比的14:00—14:20比较，不能与历史整小时比较 |

长短窗口结合是兼顾告警准确性、发现速度和恢复速度的一种设计思路；低流量场景需要单独处理，不能简单套用高流量规则。

### 3. 正常基线：不能只跟上一小时比较

建议先采用可解释的基线：

**预期订单量＝近6—8周可比星期、可比营业时段的稳健基准，经近期经营水平和已知活动计划调整。**

同时生成“正常波动区间”。小时、日、周周期和趋势都应纳入考虑，而不是采用全店统一的固定单量阈值。周期性、趋势及预期区间也是异常检测可参考的通用方法。

| 场景 | 处理方式 |
|---|---|
| 工作日与周末 | 分别比较，不把周日晚高峰与周一普通时段直接比较 |
| 活动与非活动 | 普通经营基线和活动预期曲线分开 |
| 新店 | 结合自身短期表现与同城同类型门店先验，标记低置信度 |
| 低单量门店 | 使用更长窗口、绝对差额和状态检查，不仅凭百分比报警 |
| 计划停业 | 只认可事前审批的营业计划；不能把临时误关店自动视为正常 |
| 数据缺失或延迟 | 不补成零；标记数据不足，优先触发数据质量告警 |

“缺少数据”与“指标为零”必须区分。缺失数据可能意味着采集问题，也可能是没有上报，不能直接推断业务中断。

### 4. 爆单与暴跌红黄规则

下面阈值只作为**有稳定历史的中等单量“门店×渠道”试运行示例**。设实际滚动60分钟订单量为A，预期量为E。

普通单量告警建议同时满足：**数据健康、计划营业、偏离正常区间、相对变化达标、绝对差额达标，并且近期短窗仍存在异常。**

| 类型 | 初版触发示例 | 等级及处置 |
|---|---|---|
| **健康爆单** | A≥1.5×E，且增加≥10单，但库存、拣货、配送和贡献利润均正常 | 增长提示，不作为业务故障告警 |
| **爆单黄色** | 达到爆单条件，同时拣货负荷接近产能，或核心商品库存覆盖时间接近补货周期 | 提前补货、加人、协调运力，防止风险兑现 |
| **爆单红色** | 爆单同时出现已支付订单无法备齐、超卖，或预计履约将突破关键承诺红线 | 立即组织履约与供给处置，必要时按授权调整活动或接单策略 |
| **暴跌黄色** | A≤0.7×E，且减少≥10单；最近15分钟仍偏低 | 自动生成排查清单，由门店或渠道运营核验 |
| **暴跌红色** | A≤0.4×E，且减少≥20单，近期短窗仍严重异常；或已确认营业/交易故障 | 立即升级至城市负责人及相关值班团队，不等待根因全部查清 |
| **突发断单快速通道** | 正常计划营业、预期短窗有足够订单，但实际持续为零，且营业或交易独立检查异常 | 直接红色，不必等满60分钟 |
| **低基数保护** | 预期单量很低，或历史样本不足 | 不单靠涨跌百分比报警；改用长窗口及营业、支付、库存等直接证据 |

**两条独立红线：**

**订单翻倍不等于危险。**如果利润、库存和履约均健康，应视为增长机会。

**未达到爆单涨幅，也可能发生履约危机。**实际缺货、超卖和履约硬红线必须独立检测，不能被单量条件挡住。

### 5. 爆单预警重点：提前发现缺货和履约风险

| 监控项 | 建议展示与计算方向 | 对应动作 |
|---|---|---|
| 核心商品库存覆盖 | 可售库存÷未来预测销售速度；库存需求按共享库存的全部渠道汇总 | 补货、调拨、核验库存、调整活动商品 |
| 已支付订单备齐风险 | 已支付待履约订单中，无法完整备齐的订单和商品 | 优先核实库存与处理缺货，不继续放大销售承诺 |
| 拣货负荷 | 当前待处理工作量＋未来短时预测工作量，相对于有效处理能力 | 调人、分工、调整作业安排 |
| 拣货与出库时效 | 待拣积压、最老待处理订单、耗时较长订单及承诺剩余时间 | 优先处理即将超时订单 |
| 配送承接 | 待骑手接单、长时间待取货、预计送达超时 | 协调配送资源，核验服务范围与承诺设置 |
| 爆单利润质量 | 新增订单预估单均贡献、优惠预算消耗、赔付风险 | 防止错价、过度补贴或履约费用吞噬利润 |

如果可售库存字段已经扣除了锁定库存，就不能再次扣减。若缺少库存快照或产能信息，相应检查应标为“待核验”，不能显示成“无风险”。

### 6. 暴跌自动排查清单

自动排查应输出**证据与状态**，而不是直接生成看似确定的原因。

统一使用四种检查状态：**已正常、命中异常、数据不足、待人工核验。**

| 排查顺序 | 检查内容 | 需要的证据 | 命中后的处理方向 |
|---|---|---|---|
| **1. 数据是否真实** | 订单同步、接口延迟、消息积压、重复去重、源系统与看板差异 | 数据更新时间、采集心跳、源端订单记录 | 先处理数据问题，暂停依赖失真数据的单量推断 |
| **2. 是否应当营业** | 计划营业与实际状态是否一致，是否误关店、误暂停接单 | 营业计划、状态快照、操作记录 | 核验并按授权恢复经营状态 |
| **3. 活动是否发生变化** | 活动开始、结束、撤券、预算到期是否符合计划 | 活动日历、预算、优惠配置变更 | 区分计划内回落与误操作 |
| **4. 供给是否异常** | 核心商品缺货、批量下架、价格异常、优惠不可用 | 库存、上下架、价格与优惠记录 | 补货、恢复商品、修正配置 |
| **5. 流量是否下降** | 曝光、进店是否偏离正常区间 | 平台流量数据，若可获取 | 定位流量侧问题；没有证据时不写“平台限流” |
| **6. 转化或交易是否故障** | 进店正常但下单、支付下降，是否出现错误 | 漏斗、失败记录、接口日志 | 核验价格、优惠、交易链路和系统问题 |
| **7. 履约是否限制成交** | 无运力、配送范围变化、预计时效恶化、积压导致暂停 | 履约状态、服务范围、配置记录 | 协调运力、消化积压、检查配置 |
| **8. 异常范围与变更关联** | 单店还是同城多店、单渠道还是全部渠道，异常前是否有变更 | 可比门店/渠道、配置变更时间 | 缩小排查范围；相关性只能作为候选原因 |

最终事件结论建议分为五类：

**正常波动｜经营异常｜业务系统故障｜数据故障｜尚未定位。**

例如，多家门店同时下跌只能说明影响范围较大，不能单独证明“正常市场波动”；缺少流量字段，也不能将“流量下降”写成已确认根因。

### 7. 活动白名单：调整预期，不屏蔽风险

| 白名单字段 | 必须明确的内容 |
|---|---|
| 作用范围 | 城市、门店、渠道；必要时限定商品或活动 |
| 生效时间 | 开始、结束及明确的前后过渡时段，到期自动失效 |
| 预期变化 | 活动订单曲线或合理区间，不只是“活动期间不报警” |
| 豁免范围 | 仅适用指定单量波动规则 |
| 审批信息 | 活动负责人、审批人、原因、版本及变更记录 |
| 仍需监控 | 超卖、超时、错价、交易故障、数据故障和超预算亏损 |

普通基线训练可排除已知大促、故障等特殊时段，再对活动单独建预期；异常检测中排除特殊训练时段是可参考的方法，但**训练排除不等于业务告警全部静默**。

**示例：**活动预计某小时100—140单，实际130单，不应因高于平日而报警；但如果已支付订单无法备齐，仍触发红色缺货告警。活动结束后常态预期为40—50单，实际45单，不应仅因比上一小时下降约三分之二而报暴跌。

### 8. 预警必须形成处理闭环

| 环节 | 建议机制 |
|---|---|
| 分派 | 黄色推送门店或渠道负责人；红色同步城市负责人及对应值班团队 |
| 管理层升级 | 跨城市、影响面较大、利润风险较高或处置超时事件，再升级公司管理层 |
| 响应目标 | 可先设置红色5分钟确认、15分钟给出初步方案；黄色15分钟确认、30分钟给出方案，再按实际排班校准 |
| 去重 | 同一根因形成一个事件，保留所有受影响门店和渠道，不重复群发 |
| 升降级 | 黄色升级红色立即通知；不能被普通通知冷却时间屏蔽 |
| 恢复验证 | 近期订单、营业、库存或履约恢复，并通过若干次连续检查；不机械等待60分钟滚动窗口完全清空 |
| 复盘 | 记录确认原因、采取动作、恢复时间、误报标签和规则调整 |

告警去重、分组、路由和关联抑制可以减少重复通知；但应保留受影响对象，避免“通知变少”同时变成“问题不可见”。

利润影响建议分开展示：**已发生损失、当前风险敞口、未来情景测算。**订单暴跌影响可结合缺失订单、预期完成率及正常单均贡献估算；若原本单均贡献为负，减少这部分订单可能是少亏，不能强行标成利润损失。

## 九、下钻、权限与落地验收

### 1. 统一下钻体验

每条下钻链路都继承时间、城市、渠道及口径，保留面包屑导航，返回时不丢筛选条件。

| 管理层问题 | 下钻路径 | 运营最终得到什么 |
|---|---|---|
| 为什么利润没有达到进度？ | 总览→差距来源→城市/门店→费用或订单 | 可核验的利润差额与整改对象 |
| 哪些门店应优先整改？ | 城市经营→亏损结构→门店诊断 | 门店问题、责任人及整改指标 |
| 渠道为什么增单不增利？ | 渠道→单均贡献→活动/时段→订单费用 | 优惠、商品结构和履约成本证据 |
| 哪些商品需要优先补货？ | 商品品类→核心缺货影响→SKU×门店 | 补货对象、缺口、影响订单及预期价值 |
| 为什么突然暴跌？ | 告警摘要→事件页→自动排查→源记录 | 检查状态、候选原因、已确认根因及动作 |

### 2. 权限与显示规则

管理层默认看汇总；城市负责人看授权城市；门店运营看所属门店；敏感采购成本和费用按职责授权。订单中的个人信息默认脱敏，不能因拥有经营汇总权限就自动获得全部客户明细。

红色、黄色专用于风险等级，并配文字标签；“数据不足”使用独立状态，不能显示为正常。

### 3. 上线验收重点

| 验收项 | 判断标准 |
|---|---|
| **数值一致** | 同一口径下，总览、专题和明细可核对；未归属、分摊和调整项可追溯 |
| **利润可信** | 收入、退款、补贴、成本不重复；预估与结算明确区分 |
| **管理层可决策** | 不进入订单明细，也能看懂盈利、差距、风险和资源投向 |
| **运营可执行** | 告警和关键差距能下钻到证据、责任人和处理动作 |
| **预警有效** | 回放普通日、活动开始/结束、夜间低单量、误关店、断流、缺货与履约积压等场景 |
| **整改有闭环** | 每个重要事件有确认、处置、恢复和复盘记录，并持续评估误报、漏报与响应耗时 |

**全量数据不等于实时数据。**若某些字段只有日批更新，就不能通过每5分钟刷新页面宣称具备实时监控；小时级预警需要相应的事件或状态数据在小时内可靠到达。

## 简短汇报总结

本次看板建设以**利润优先、管理决策优先**为原则，采用一套数据底座、三级展示结构，形成经营总览、城市门店、利润成本、渠道订单、商品品类五大模块，并配置小时级经营预警中心。

管理层重点掌握盈利结果、目标差距、资源投向和重大风险；运营通过下钻定位到门店、渠道、商品与订单，完成整改。爆单预警重点保护库存和履约，暴跌预警通过数据核验、自动排查及活动白名单减少误报，最终形成**发现问题—明确责任—执行整改—验证恢复**的经营闭环。

可以。下面这版我按“可直接交给产品经理、BI、UI、数据研发共同落地”的标准整理，重点不是做一块炫酷大屏，而是做成一套**高管5秒看懂、30秒判断、运营3分钟定位问题**的即时零售经营驾驶舱。

# 即时零售企业经营大屏完整设计方案

## 一、产品定位

### 1. 核心目标

这套大屏不是传统意义上的“数据展示墙”，而是：

> **以利润为第一优先级，以经营目标为主线，以异常风险为驱动，以运营下钻为闭环的即时零售经营驾驶舱。**

整体用户结构：

| 用户 | 使用占比 | 主要诉求 |
|---|---:|---|
| 公司管理层 | 80% | 盈利多少、目标差多少、哪里出问题、哪里值得投入、现在要不要干预 |
| 城市/运营负责人 | 20% | 哪个城市、门店、渠道、商品出了问题，原因是什么，怎么整改 |

因此设计必须坚持：

**首页服务管理层，明细服务运营。**

管理层不应该面对海量表格和SKU；运营也不应该另外建设一套数据体系。

---

# 二、整体设计理念

## 1. Apple级视觉设计原则

这里的“Apple级”不是模仿苹果官网，而是采用类似的产品设计思想：

| 原则 | 在本项目中的体现 |
|---|---|
| 信息优先于装饰 | 不做发光地图、3D柱状图、旋转地球等无决策价值元素 |
| 极强视觉层级 | 利润 > 目标差距 > 风险 > 增长 > 过程指标 |
| 克制用色 | 普通数据以灰、白、蓝为主，红色只留给真正的异常 |
| Progressive Disclosure | 首页给结论，点击后逐层展开原因和明细 |
| 一屏一个判断 | 每个模块都必须能够形成明确经营结论 |
| 默认状态即最佳状态 | 管理层打开大屏无需调筛选器就能获得正确全局视角 |
| 异常优先 | 正常业务保持安静，真正的问题主动跳出来 |

整个界面禁止采用传统BI常见的：

**满屏框线、荧光蓝、渐变大标题、3D饼图、仪表盘、复杂地图、超过8种颜色。**

# 三、屏幕及页面规格

## 1. 基础分辨率

以：

**1920 × 1080，16:9**

作为标准设计稿。

同时兼容：

2560 × 1440  
3840 × 2160

但4K屏不要简单同比缩小字号，应保持有效信息密度。

---

## 2. 页面栅格

建议采用：

**24列栅格系统**

页面参数：

| 项目 | 建议 |
|---|---:|
| 左右安全边距 | 40–48px |
| 模块间距 | 16px |
| 大模块间距 | 24px |
| 顶部导航高度 | 64px |
| 全局筛选区 | 48–56px |
| 卡片圆角 | 12px |
| 卡片内边距 | 20–24px |

卡片不要全部加边框。

优先使用：

**背景明度差 + 轻微描边**

建立层级。

# 四、视觉色彩规范

## 1. 推荐默认主题：深色经营驾驶舱

即时零售大屏通常长时间展示，同时存在大量实时数据，因此建议默认使用深色模式。

### 基础色

| 用途 | 色值 |
|---|---|
| 一级背景 | `#0B0D10` |
| 二级背景 | `#111419` |
| 卡片背景 | `#171B21` |
| Hover/选中背景 | `#20252D` |
| 一级文字 | `#F5F7FA` |
| 二级文字 | `#AAB2BD` |
| 辅助文字 | `#747D89` |
| 分割线 | `#282E36` |

原则：

**不是纯黑背景，也不是满屏蓝色。**

---

## 2. 功能色

### 主交互色

品牌和操作统一使用：

**科技蓝：`#4C8DFF`**

用于：

筛选器、选中状态、可下钻提示、主要趋势线、按钮。

不要拿蓝色表示“业务表现优秀”。

---

### 盈利正向

**Profit Green：`#32D583`**

只能用于：

盈利  
正贡献  
目标超额完成  
明确改善

不能因为订单上涨就自动变绿。

---

### 黄色预警

**Warning Amber：`#F5B942`**

用于：

风险接近阈值  
目标有偏差  
爆单产能承压  
库存即将不足  
需关注但尚未失控

---

### 红色严重异常

**Critical Red：`#FF5A5F`**

只用于：

严重亏损  
暴跌  
无法履约  
超卖  
系统故障  
严重目标偏差

红色必须克制。

否则管理层很快会产生“告警疲劳”。

---

## 3. 数据系列颜色

正常分析图表最多同时使用5组颜色：

| 系列 | 颜色 |
|---|---|
| 主指标 | `#75A7FF` |
| 第二指标 | `#6FCDBB` |
| 第三指标 | `#A897D8` |
| 第四指标 | `#E6BC70` |
| 对比基准 | `#7E8793` |

禁止每个城市一个颜色。

城市比较应该用：

**统一颜色 + 强调异常对象。**

---

## 4. 状态表达

颜色不能作为唯一识别信息。

例如：

🔴 严重  
🟡 关注  
● 正常

UI中同时显示：

**颜色 + 图标 + 状态文字**

避免只有一个红点。

---

# 五、字体和数字规范

推荐字体：

中文：

**PingFang SC / Microsoft YaHei**

数字及英文：

**SF Pro / Inter**

### 字号层级

| 类型 | 字号 |
|---|---:|
| 页面标题 | 28–32px |
| KPI核心数字 | 38–46px |
| KPI辅助数字 | 20–24px |
| 卡片标题 | 16–18px |
| 正文/图表轴 | 14–16px |
| 辅助说明 | 13–14px |

大屏场景尽量不要出现低于13px的核心信息。

---

## 数字格式

金额统一：

¥328.6万  
¥1.28亿

订单：

12.8万单

比例：

18.6%

利润：

+¥38.2万  
-¥12.4万

管理层页面最多保留：

**1位小数。**

没有必要展示：

¥1,285,392.87

# 六、整体信息架构

一级导航建议固定为：

| 页面 | 核心问题 |
|---|---|
| 01 经营总览 | 公司今天/本月到底经营得怎么样 |
| 02 城市门店经营 | 问题和机会在哪里 |
| 03 利润成本拆解 | 钱到底赚在哪、亏在哪 |
| 04 渠道订单大盘 | 哪些订单是高质量订单 |
| 05 商品品类大盘 | 哪些商品真正创造利润 |
| 06 经营预警中心 | 现在有什么事情必须处理 |

订单列表、SKU列表、费用明细、履约轨迹：

**不进入一级导航。**

全部通过下钻进入。

---

# 七、全局顶部区域

所有页面统一顶部结构。

```text
┌────────────────────────────────────────────────────────────────────┐
│ 即时零售经营驾驶舱        数据截止 14:10 ●正常          管理视图   │
├────────────────────────────────────────────────────────────────────┤
│ 本月累计 ▼   全国 ▼   全部门店 ▼   全渠道 ▼     对比：目标 / 上期 │
└────────────────────────────────────────────────────────────────────┘
```

必须始终展示：

**数据截止时间。**

例如：

> 数据更新至 14:10  
> 实时订单延迟 2 min  
> 财务结算更新至 T-1

这样可以避免管理层把T+1成本和实时订单错误地放在一起判断。

# 八、页面一：经营总览

## 面向角色

CEO、总经理、业务负责人、财务负责人。

## 页面目的

打开大屏后5秒回答：

**赚没赚钱？目标能不能完成？哪里拖累？有没有重大风险？**

---

## 第一屏布局

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 公司经营利润 │利润目标差│月底预测│利润率│单均贡献│亏损门店          │
├───────────────────────────────┬──────────────────────┬───────────────┤
│                               │                      │               │
│      利润实际 VS 目标趋势      │   利润差距来源        │   经营风险    │
│                               │                      │               │
├───────────────────────────────┼──────────────────────┼───────────────┤
│       城市经营矩阵             │   渠道盈利结构        │ 品类盈利结构  │
└───────────────────────────────┴──────────────────────┴───────────────┘
```

---

## 顶部6张核心卡

### ① 公司经营利润

展示：

**¥328.6万**

辅助：

目标 ¥350万

较目标：

**-21.4万**

这是首页第一指标。

---

### ② 利润目标差

不要只显示：

94%

应该显示：

**-21.4万**

并附：

进度差：

-6.1%

因为管理者最终关心的是：

**差多少钱。**

---

### ③ 月底利润预测

展示：

预计：

**¥342–358万**

目标：

350万

同时显示：

**达标概率 / 风险状态**

而不是提供虚假的单点精确数字。

---

### ④ 经营利润率

利润 / 经营净收入。

同时显示目标差异。

---

### ⑤ 单均贡献利润

例如：

**¥4.83 / 单**

同时显示：

昨日 ¥5.02

用于识别：

订单增长是否正在牺牲利润。

---

### ⑥ 亏损门店

例如：

**18家**

累计亏损：

¥42.6万

点击进入：

城市门店经营。

# 十、利润差距来源

推荐：

## Waterfall瀑布图

展示：

```text
目标利润
   ↓
订单规模
商品毛利
平台费用
营销投入
履约成本
退款赔付
固定成本
   ↓
```

而不是只看到：

“利润下降6%”。

# 十一、经营风险区域

右侧固定设置：

## 今日经营风险

示例：

```text
🔴 上海   3店订单暴跌     预计利润影响 -2.8万
🔴 杭州   2店核心SKU断货  预计影响订单 186单
🟡 苏州   配送产能接近上限
🟡 成都   利润目标落后 8.6%
```

这里只显示：

**Top 3–5重大事件。**

不展示几十条告警。

点击进入预警中心。

# 十二、城市经营矩阵

推荐使用：

## 四象限散点图

X轴：

收入/订单增长率

Y轴：

经营利润率

气泡大小：

经营收入

每个点：

一个城市。

形成四种类型：

```text
              高利润
                 ↑
   保利润        │       加资源
                 │
增长下降 ────────┼──────── 增长
                 │
   重点整改       │       增收不增利
                 ↓
              低利润
```

这是非常适合管理层的一张图。

比中国地图更有决策价值。

分成：

**下降盈利**

# 二十、爆单预警

爆单不能只判断：

订单上涨50%。

必须判断：

**订单增长 + 库存承接 + 履约产能。**

### 黄色

# 三十九、设计验收标准

上线前不要只验收：

“页面是否漂亮”。

应该验收下面五件事。

| 项目 | 验收问题 |
|---|---|
| 5秒识别 | CEO能否5秒判断今天业务好坏 |
| 30秒决策 | 能否30秒定位最严重问题 |
| 数据一致 | 首页、专题、明细是否可以完全对账 |
| 问题定位 | 一个利润异常能否3分钟钻到具体原因 |
| 预警有效 | 是否真正发现问题而不是制造大量噪音 |

最终目标不是：

> “领导觉得大屏漂亮。”

而应该是：

> **经营会议直接围绕这块屏幕进行。**

# 四十、最终设计总结

这套即时零售大屏应形成一个非常明确的信息体系：

**第一层：经营结果**

利润、目标差距、月底预测。

↓

**第二层：问题来源**

城市、成本、渠道、商品。

↓

**第三层：经营风险**

爆单、暴跌、缺货、履约、亏损。

↓

**第四层：运营诊断**

门店、小时、SKU、订单、费用。

↓

**第五层：整改闭环**

问题 → 责任人 → 动作 → 恢复 → 复盘。

因此整套产品最终不是六张孤立BI页面，而是一个完整的经营系统：

> **发现结果 → 判断差距 → 找到原因 → 识别风险 → 下钻问题 → 推动整改。**

视觉设计上采用深色、克制、高信息层级的“企业级Apple风格”，不追求传统数据大屏的炫技感，而追求三个结果：

**一眼看懂。**  
**一眼找到问题。**  
**一眼知道下一步应该做什么。**

这版已经可以作为**产品PRD + BI方案 + UI设计规范的第一版输入**。下一步最值得继续细化的是把这6个页面逐页画成 **1920×1080 Figma级线框稿**，精确到每个卡片的尺寸、位置、字段、图表和交互状态；这样就可以直接交给设计师和BI开发。


下面是加入地图后的完整修订版。我把地图放在**经营总览核心区域**和**城市门店经营页**，但不让它替代利润矩阵、排名和预警，而是承担“空间定位 + 风险态势 + 下钻入口”的作用。

# 即时零售企业经营大屏完整设计方案｜地图增强版

## 一、产品定位

这套大屏定位为：

> **以利润为第一优先级，以目标差距为经营主线，以地图呈现全国经营态势，以异常预警驱动行动，以运营下钻完成整改的即时零售经营驾驶舱。**

用户结构：

| 用户 | 使用占比 | 核心诉求 |
|---|---:|---|
| 公司管理层 | 80% | 盈利多少、目标差多少、哪个城市有问题、哪里需要资源、是否存在重大经营风险 |
| 城市/运营团队 | 20% | 哪个城市、门店、渠道、商品异常，原因是什么，如何整改 |

设计原则：

**首页管理决策化，专题经营分析化，明细运营执行化。**

# 二、整体设计理念

## 1. 视觉原则

采用克制、清晰、安静的高级企业级设计风格。

核心原则：

**利润优先于规模。**

**异常优先于常规指标。**

**地图服务决策，不服务装饰。**

**首页只呈现结果、差距、区域态势和风险。**

**订单、SKU、费用流水全部通过下钻进入。**

避免传统大屏常见问题：

- 巨型发光地图
- 3D柱状图
- 旋转地球
- 蓝色霓虹描边
- 满屏红黄绿
- 地图占据50%以上空间但没有决策信息
- 地图颜色与经营指标没有明确关系

# 五、地图视觉规范

地图是新增的核心视觉元素，但必须遵循经营信息设计原则。

## 1. 地图类型

首页推荐使用：

### 中国城市经营态势地图

采用：

**低对比度行政区域底图 + 城市经营气泡 + 风险状态环**

不要使用大面积省份渐变热力图作为唯一编码。

原因：

你们实际经营主体是：

**城市 → 门店**

而不是单纯的省份。

---

## 2. 地图数据编码

每个经营城市表现为一个气泡。

### 气泡大小

默认表示：

**经营净收入规模**

不建议表示订单量，因为订单多不代表价值高。

### 气泡填充颜色

表示：

**经营利润率 / 盈利状态**

例如：

绿色：盈利健康

灰蓝：正常

黄色：目标偏离或低利润

红色：严重亏损

### 外圈

表示：

**经营风险等级**

例如：

红色外环：

存在红色重大告警。

黄色外环：

存在黄色预警。

无外环：

无重大风险。

---

## 3. 地图单点信息

悬停或点击城市时显示：

```text
杭州

经营利润      ¥62.8万
目标差额      -¥6.4万
经营利润率    6.8%
完成订单      18.6万单
亏损门店      4家

🔴 重大风险 1
🟡 关注风险 3
```

# 十八、不建议使用简单热力地图的原因

传统省份填色地图容易出现几个问题：

第一：

一个省面积很大，但业务规模可能很小。

第二：

视觉面积会放大西部区域的重要性。

第三：

无法清晰表达：

城市规模 + 利润 + 风险

三个维度。

所以建议使用：

> **低对比行政底图 + 城市气泡**

作为核心地图。

省份面色仅作为辅助。

# 三十五、地图设计最终结论

地图值得加入，而且对于即时零售这样的：

**多城市、多门店、高实时性**

业务非常有价值。

但地图的正确角色不是：

> “让大屏更像大屏。”

而应该是：

> **帮助管理层一眼判断经营问题发生在哪里。**

因此建议整个系统形成：

**地图看空间**

＋

**趋势看变化**

＋

**矩阵看经营质量**

＋

**瀑布看利润原因**

＋

**预警看实时事故**

＋

**下钻看具体明细。**

最终做到：

> **全国一张图看经营态势，一次点击进入城市，一次下钻到门店，一次诊断找到问题。**

这才是地图元素在即时零售企业经营大屏中的真正价值。

视觉上，我建议把地图控制在首页核心区域约 **35%–40%的有效视觉面积**，足够形成“大屏感”，但不会压过利润和风险信息。最关键的是地图默认使用**利润态势模式**，而不是GMV热力图。
