# 自动化脚本经验沉淀（nr.ele.me / 翱象）

> 每次踩坑后更新此文档。目标：同类问题不再重复排查。

## 1. nr.ele.me（淘宝闪购商家后台）通用

### 1.1 入口：永远走菜单点击，不直跳 hash 路由
- `#/pc/dataDownloadCenterIIPc/`、`#/pc/homePagePc/` 等只是**外壳路由**，业务内容装在 iframe
  （下载中心：`ms.ele.me/app/tbsg-merchant/ebai-download-center/...`）里。
- 直接 `page.goto()` 跳 hash 会导致外壳加载但 iframe 不初始化（现场：只剩“切回旧版”+ AI 助手 frame，
  无业务 frame）。教训：`nr-history2-failed.txt` 当时 3 个 frame 里根本没有 `ebai-download-center`。
- 正确姿势：`goto(ROOT_URL)` → 点左菜单（`数据` → `数据下载中心`）→ 等 iframe 就绪（`dcFrame()`）。

### 1.2 登录：协议弹窗是拦截式的
- 点「登录」不直接跳转，而是弹「请先阅读并同意商家端《隐私政策》」→ 必须点「同意」才会真正提交。
- 处理：提交前后各扫一遍弹窗；等待循环里检测到弹窗 → 点「同意」→ **重新点一次「登录」**，最多 5 次
  （见 `nr-login.mjs handleAgreementDialog`）。
- 定位不用固定 class（`ant-modal` 可能带 shadow DOM）：先找含「请先阅读并同意 / 隐私政策」文本的弹层，
  再取其中「同意/确定/继续登录」按钮坐标，用真实鼠标点击。
- 登录按钮上方还有「已阅读并同意」复选框，也要自动勾选。两条路径都覆盖。
- 凭据放 `automation/.env`（`NR_ACCOUNT` / `NR_PASSWORD`），该文件已被 `.gitignore` 忽略。

### 1.3 会话会过期，先探活再干活
- 现场：`.browser-data/nr` 失效后首页只剩“切回旧版”，连左菜单都没有，
  下载脚本报 `菜单项未找到或不可点：数据`。
- 定时任务顺序：先跑 `nr-login.mjs` 探活（输出含公司名=正常，仅“切回旧版”=已失效），
  失效则清目录重登（协议弹窗会自动同意），再跑业务脚本。
- Chrome 顶部 `--no-sandbox` 警告是 Playwright 启动参数所致，不影响功能，忽略。

### 1.4 iframe 页面抓取：文本定位 + 坐标点击
- React 重渲染会导致 Playwright 定位器失效：统一用 `frame.evaluate` 找文本、算坐标，
  再用 `page.mouse.click(x, y)` 真实点击。
- ant-design 控件（tab / radio / checkbox / select）状态以 DOM 属性为准
  （`input.checked`、`metricStats()`），**不看按钮文字**（现场：勾选 8/8 但按钮仍显示“已选0”，文案异步刷新）。

## 2. 下载中心（ebai-download-center）专用

### 2.1 轮询必须用独立时钟（血泪教训：空转几小时）
- `page.waitForTimeout()` 在页面关闭时会**立即抛异常而不是等待**。
  catch 里只打日志就继续循环 → 60 秒等待窗口被压缩成几秒内上百次空转
  （现场：`页面已关闭，靠目录轮询兜底` 刷屏上百行）。
- 规定：所有轮询等待一律用 `sleep = (ms) => new Promise((r) => setTimeout(r, ms))`，
  再加 `MAX_POLLS` 迭代上限 + 总 deadline 双保险。

### 2.2 历史任务必须按生成时间戳锁定本轮
- 历史表格是追加的，多次运行留下多个同名文件（现场：11:43/11:46/11:49/11:54 四个
  `流量分析-分来源数据下载_...`，全 31.04kB——重复生成了 4 次相同文件）。
- 规定：点生成前记录 `genStamp = Date.now()`，只接受 `任务日期 >= genStamp` 且已生成的行；
  没有就继续等，**绝不点旧行**。`parseTaskTs()` 解析 `YYYY-MM-DD HH:mm:ss`，解析失败返回 0（不过滤掉，防误杀）。
- 教训：光写注释 `// 用于锁定这一次的任务` 但不实现等于没写。

### 2.3 下载返回路径只有一条（单链路）
- 禁止 `Promise.race` 套两个 `waitAndDownload`：两个分支抢 `page.waitForEvent('download')`，
  先返回的 `null` 会覆盖已落盘的成功结果（现场：日志末尾既有 `导出成功` 又有 `未能在下载历史中获取文件`）。
- 规定顺序：先挂 `download` 监听 → 再点按钮 → 目录轮询确认（独立时钟 60s）→ 事件兜底（`download.saveAs`）。
  目录命中即返回；事件拿到也 `saveAs` 落盘再返回。

### 2.4 落盘立即归档重命名
- 平台文件名是 `类型_商户id_时间戳_随机.xlsx`，多次运行堆在一起分不清。
- 规定：落盘后立即重命名为 `类型_起止日期.xlsx`
  （如 `流量数据下载_2026-09-20-2026-09-21.xlsx`），见 `archiveName()`。

### 2.6 下载按钮会杀死页面：捕获 URL 后用原生 fetch 直拉（2026-09-22 实测）
- 现场：历史里的「下载」是无 href 的 `<button class="ant-btn ant-btn-link">`（JS 驱动），一点就整页导航，
  frame 操作全抛异常（行数读出 -1）、`download.saveAs` 报 `Target page, context or browser has been closed`、
  落到下载目录的半成品在 close 时被回收——表现为“脚本内看到文件、退出后文件消失”。
  小文件偶尔能抢在页面死前完成（流量 31KB 成功），大文件必死（商品 52KB 连死 4 次）。
- 规定动作（三通道，缺一不可）：
  1. 点之前 `page.on('request')` 捕获真正的下载地址（实测是免鉴权的 OSS 直链
     `kbtdatacenter.oss-cn-zhangjiakou.aliyuncs.com/.../*.xlsx`），同时把 URL 写入
     `output/last-download-url.txt` 方便手动 curl 兜底；
  2. 点之后立刻 `saveAs`（页面活着时最快），失败就转通道 3；
  3. **用 Node 原生 `fetch` 直拉 OSS 链接、落盘**——不依赖页面/context 存活，这是最终成功的通道。
     不要用 `context.request`（页面死后它一样报 closed）。
- 页面死后不要 `page.reload()`（SPA 会落回空白外壳，即 1.1 的坑），要 `goto(ROOT_URL)` + 重新点菜单重进。
- `launchPersistentContext` 必须显式传 `downloadsPath: downloadDir`，否则下载进系统临时目录，
  close 时被 Playwright 回收。
- 体积稳定校验（两次 stat 一致且 >0）后再认领文件；落盘后立即再 copy 一份到
  `output/nr-download-center-keep/`，双保险。
### 2.7 已验证的数据口径（2026-09-22）
- 商品 tab：`商品数据下载` + `自定义 2026-08-23~2026-09-21` + `按店铺明细下载` + `店铺数据` + `按每日统计`（红线，绝不能选“按筛选时间汇总”）+ 全选 9 指标 → `output/nr-download-center/商品数据下载_2026-08-23-2026-09-21.xlsx`：`data` 表 664 行，30 个独立日期（20260823~20260921），列=日期/门店名称/门店id/在架/可售/动销/缺货/退款/差评/出勤率/缺勤数/缺勤损失金额。行顺序不按日期排，属正常。（`--data-dim=` 可覆盖数据维度；流量默认分来源数据，商品默认店铺数据。）

- 流量 tab：`流量数据下载` + `自定义` + `按店铺明细下载` + `分来源数据` + `按每日统计` + 全选 8 指标

## 3. MySQL 入库链路（2026-09-22 落地）

> 目标：数据量随每日累计增大，看板不再读本地文件夹，统一从 MySQL 读。
> 链路：**抓取 → `output/` 归档 xlsx（原始凭证保留）→ `scripts/db-import.mjs` → `dashboard` 库 → 看板从库读**。

- 环境：本机 MySQL 8.4（`E:\MySql`，服务 `MySQL84`），`127.0.0.1:3306`，`root`，库 `dashboard`
  （Navicat 同名连接，截图参数）。连接参数在 `automation/.env`（`DB_*`，已 gitignore，
  命令行不再传密码）。
- 建库：`database/mysql-schema.sql`，9 张表（`dim_store` + 7 张事实表 + `refresh_state` 水位表），
  `utf8mb4`。旧 PostgreSQL 原型已经归档到 `archive/postgresql/`，不再是可选生产链路；
  看板与自动化统一使用 MySQL `dashboard`。
- 入库命令：`npm run db:import`（全量 7 集）；单集 `--dataset=traffic|product|reverse|ax_business|ax_profit|ax_margin|ax_quality --file=…`；
  `--date=` 覆盖业务日期（`ax_profit`/`ax_quality` 无日期列时用，默认=导出时间前一天）。
- 幂等可重跑：`INSERT … ON DUPLICATE KEY UPDATE`；`refresh_state.row_count` 存表内真实行数，
  重跑不累加；比率存小数；逆向单条码/原因放宽 512 字符（实测有多条码逗号拼接超 64 字符）。
- MySQL 独有坑：`UNIQUE KEY (store_code, platform)` 中 `''` 会互斥（MySQL 认为空串相等），
  未知编码必须存 NULL——`dim_store` 曾因此只进 1 行（`Duplicate entry ''`），改 NULL 后 31 家正常。
- 导入后必查：`SELECT dataset, latest_biz_date, row_count FROM refresh_state`，
  `latest_biz_date` 到昨天才算当日链路闭环。

### 3.1 看板指标 ↔ 表对照（防膨胀审计，2026-09-22）
- 看板 JSON 由 `scripts/sync-db-to-json.mjs` 从 MySQL 生成，审计：`trafficData` 要流量 12 列全用且来源分类白名单仅
  `分平台渠道/淘宝闪购APP内渠道`；`source1` 要周期数据 9 列 + 店铺汇总 11 列全用 + 商品明细 12 列；
  `profitPc/orderMargin/cost/risk` 各取翱象三表所需列（JSON 包已是最小收纳）。
- 结论：nr 三表**无冗余列可删**；`fact_reverse_order` 看板暂无消费（订单毛利走翱象口径），保留作逆向分析；
  门店追踪/上线进度是手工数据源，不在自动链内。
- `fact_product_item_period`（周期汇总专用）：商品数据维度（35 指标）无时间维度选项，
  20260823~0921 导出 103044 行日期列全是 `20260823-20260921`——**这是汇总不是明细，不进日趋势表**。
  如需按日品类，须拆 30 个单日任务（`起止相同→day`），量大，不建议日更。

### 3.2 粒度铁律（入库前 grain 校验，与看板 `sync-traffic-data.py` 同口径）
- `YYYYMMDD`→day；`YYYYMMDD-YYYYMMDD` 起止相同→day、不同→period；起止倒挂抛错。
- 日明细+汇总混排→跳过汇总行；纯 period 文件→**抛错拒绝入库**；流量未知来源分类→抛错。
- 抓取侧配合：`按每日统计` 能选必须选；规则已改为“明确选中按筛选时间汇总才停”，
  无时间选项时放行但导出后验日期列；大任务生成慢（商品明细 18MB 约 10 分钟），
  用 `--history-only --match=文件名片段` 蹲守取回。
